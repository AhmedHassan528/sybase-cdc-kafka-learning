Protocol learned from the wire

SAP documents LTL only up to version 700. Everything below was captured from the real RepAgent with the probe tool and raw message dumps, and it is covered by unit tests built on those captures.

sequenceDiagram
  participant RA as RepAgent (ASE)
  participant CN as Connector (CDC_RS)
  RA->>CN: TDS login (rs_user, packet size 2048, iso_1)
  CN-->>RA: LOGINACK + CAPABILITY + ENVCHANGE packet size 2048
  RA->>CN: connect source lti "MYSYBASE"."phoenix_test" 760 passthru
  CN-->>RA: result 1: VERSION 760 / result 2: Sysversion 1600 + UpgradeLocater
  RA->>CN: get maintenance user for "MYSYBASE"."phoenix_test"
  CN-->>RA: cdc_maint
  RA->>CN: get truncation "MYSYBASE"."phoenix_test"
  CN-->>RA: 36-byte OQID (last transaction Kafka acknowledged)
  loop every batch
    RA->>CN: distribute 1 time,4 oqid,6 xid begin / applied / commit ...
    CN-->>RA: DONE (exactly one per TDS message)
  end
  RA->>CN: get truncation (about every 15 s)
  CN-->>RA: acked OQID, never past unconfirmed data

How delivery safety works

flowchart TB
  C["COMMIT arrives for xid"] --> D{"commit OQID <= last queued?"}
  D -- yes --> X["skip: re-sent after reconnect"]
  D -- no --> R["register in AckTracker
(N records pending)"]
  R --> Q["queue → poll()"]
  Q --> O["records 1..N-1 carry the previous safe offset
record N carries this commit OQID"]
  O --> K["Kafka acks each record → commitRecord()"]
  K --> W{"all records of this and every earlier txn acked?"}
  W -- no --> H["truncation point stays"]
  W -- yes --> M["watermark = this commit OQID
next get truncation returns it"]

Only the last record of a transaction may claim the transaction is done. Scenario 6b proved this: after a crash with 53,822 of 200,000 records written, the stored offset was still the previous transaction and the whole transaction was re-sent.

Open items before OpenShift / production

Connect heap

Connect reached 1,954 MiB with 10,000-row transactions against the default 2 GB heap. Size the pod for the largest Phoenix transaction, or cap rows per transaction.

Kafka outage restarts the task

A broker outage longer than the group session timeout revokes and restarts the task. Data stays safe; expect duplicates and a RepAgent reconnect.

At-least-once

Duplicates after hard failures are expected (495 and 53,822 in tests 4b and 6b). Consumers de-duplicate on source.oqid. Kafka exactly-once source support (KIP-618) is the next improvement.

Password and network

Encrypted RepAgent login is not implemented. Use TLS or a NetworkPolicy that admits only the ASE host to port 11752.

Log emergency

dbcc settrunc('ltm','ignore') was not run. It discards un-replicated changes and must stay a manual DBA decision, followed by a re-baseline.

Validate on SP04 PL07

The local image is SP02 PL02. Re-capture LTL with -Dltl.dump.dir on SP04 and rerun the parser tests before go-live.

Measurement limits
  • ASE, RepAgent and connector samples were taken about every 6.5 s (5 s sleep plus query time); Kafka end offsets about every 11 s because each read starts a JVM tool.
  • Kafka Connect's REST /offsets still shows one stale record written before the TreeMap fix. The task reads the current key; the offsets topic shows 71 commits during run 3.
  • Scenario 4's first two attempts did not exercise a live session (RepAgent was still reconnecting, or the load finished first) and are not counted; 4b is the valid run.
