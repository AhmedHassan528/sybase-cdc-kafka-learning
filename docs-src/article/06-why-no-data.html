Why is there no data?

You changed a row and the topic stays empty. This section is organised by symptom. Two of the cases are reproduced with scripts in lab/experiments/ and their output is real. Those scripts and await-event.sh are bash only; on Windows run them in Git Bash. The others come from the original project and are marked so you know which is which.

Find the layer first

A change passes through seven places. Check them in order; the first one that is wrong is your problem.

Symptom: the row is in ASE, the topic exists, but this row is missing

Cause: the table is not in table.include.list.

Reproduce: lab/experiments/no-data-table-not-included.sh removes customer from the list, inserts a row, waits 60 seconds, and then adds customer back. Full output: evidence/16-no-data-table-not-included.txt.

What I saw: with customer missing from the list, no event arrived within 60 seconds. After I added customer and wrote a second row, both rows arrived, with the same ts_ms. So the row written while the table was missing was not lost in this run.

Why, as far as I can tell: from reading SybaseCdcSourceTask.java, a transaction whose rows are all filtered out still moves the acknowledgement watermark reported to ASE, but Kafka Connect only stores an offset for rows that were actually published. After the restart that the config change causes, ASE can send those rows again, and this time they pass the filter. I read this in the code; I did not run a separate test that proves it. Do not rely on either outcome: if you need a table, put it on the list before its changes happen.

Fix: lab/env/set-tables.sh payment,customer, then make a new change and wait for it with lab/env/await-event.sh.

Symptom: nothing arrives while the connector is not running

Cause: the connector task is paused, failed or restarting. ASE keeps its log; the changes are not lost.

Reproduce: lab/experiments/no-data-connector-paused.sh pauses the connector, inserts a row, waits 30 seconds, then resumes. Output: evidence/17-no-data-connector-paused.txt.

What I saw:

  • Status while paused: connector=PAUSED task=PAUSED, and no event after 30 seconds.
  • ASE's view at the same time: sleeping, retry_count 0, last_error 0. Nothing looked wrong from ASE.
  • After resuming, the event arrived 8 seconds later. That is about the 10-second retry timeout the lab sets for the RepAgent. With ASE's default of 60 seconds you would wait about a minute or longer.

Fix: resume or repair the connector. Nothing needs replaying.

Symptom: after changing the connector config, the next change is slow to arrive

Cause: a config change restarts the task, which closes the connection from RepAgent. ASE notices only when it next has something to send. In the connector log you see LTL server on port 11752 stopped and then LTL server listening, and the line RepAgent connected appears only after the next change. In the ASE error log the same moment shows RepAgent(4): Received the following communications error message ... network packet layer, which is ASE finding the old connection dead.

I saw these log lines in the container logs while running the experiments; I did not save them as an evidence file, so treat them as an observation, not a record.

Fix: none needed; it is expected. The lab sets retry timeout to 10 seconds so the wait is short (the original project saw minutes with the default). In scripts, write a change and wait for it with await-event.sh instead of waiting for a reconnect that will not happen on its own.

Symptom: nothing arrives right after ASE itself was restarted

Cause: the source database was down or starting. The pipeline is fine; it is waiting for ASE.

Reproduce: lab/experiments/source-restart.sh (bash only) writes a row, starts a wait for the next row, restarts the ASE container with docker restart (a normal stop and start; I did not kill ASE, not run), and then writes the next row. Output: evidence/28.

What I saw:

  • ASE accepted logins again 6 seconds after the restart began.
  • The wait that was already running when ASE restarted ended after 15 seconds, successfully, with the row written after the restart. It neither hung nor timed out.
  • Both rows (before and after the restart) are in Kafka exactly once, and ASE holds the same two rows.
  • ASE's RepAgent was running again without anyone starting it (sp_help_rep_agent showed it sleeping, its idle state), and the connector stayed RUNNING.

What to do: wait; do not restart the connector or start the RepAgent by hand. Keep your own waits bounded, as await-event.sh does: it stops with its own TIMEOUT message instead of waiting forever. A long ASE outage, an ASE crash and a restart of the whole Docker host were not tested (not run).

Check yourself

1. The connector is paused and ASE's RepAgent status looks healthy. Where do you look next?

At the connector: its status through the Connect REST API and its log. ASE does not know the connection is dead until it sends.

2. You add a table to table.include.list. Is it safe to assume rows written earlier will appear?

No. In my run they did, but the reason is a side effect of the restart. Add tables to the list before their data changes.
