Sybase ASE fundamentals and database setup

Plain definition: SAP Adaptive Server Enterprise (ASE) is a relational database server: one running server process (here dataserver, named MYSYBASE) hosts several databases (master, phoenix_test…), each containing tables, procedures and users. Clients talk to it with SQL over the TDS protocol (isql, JDBC, the Phoenix application). Here: ASE is the source of all changes; the connector never logs in to it.

Server, database, objects

  • Server: the dataserver process and its configuration (sp_configure), listening on port 5000. Its name (@@servername = MYSYBASE) is what RepAgent reports to the connector.
  • Devices: files ASE stores data in (disk init). This project created phoenix_data (1 GB) and phoenix_log (512 MB).
  • Database: a set of objects with its own transaction log. phoenix_test stores data on phoenix_data and its log on phoenix_log, so log growth can be measured on its own.
  • Objects: tables, indexes, procedures, owned by a database user (usually dbo, the database owner).
  • Transaction: a group of changes that becomes visible and durable together at commit, or disappears at rollback. Without begin tran, each statement is its own transaction (ASE's default "unchained" mode). One insert … select of 10,000 rows is therefore one transaction (verified in test 6: 100 statements → 100 transaction ids × 10,000 rows).

Logins, users and roles

ASE separates identities on two levels:

Login (server level)
An account that can connect to the server, stored in master..syslogins (create login … with password …). Example: sa.
User (database level)
A login mapped into one database (sp_adduser <login> inside that database). Permissions on tables are granted to users.
Role (server level)
A bundle of system privileges granted to logins: sa_role (administrator), sso_role (security officer), replication_role (replication administration).
Verified least privilege for RepAgent administration (test on SP02, evidence 12) A login with only replication_role, mapped as a user in the database, could run sp_help_rep_agent, sp_config_rep_agent and query sp_setreptable. A login with only table permissions was refused with "Only the System Administrator (SA), the Database Owner (DBO) or a user with replication_role authorization can execute…". Not tested: sp_start_rep_agent/sp_stop_rep_agent, sp_setreptable … true and sp_configure 'enable rep agent threads' (server-wide, assume sa_role). Re-test on SP04.

The initialisation scripts, line by line

sybase/00_database.sql

1–2use master / go: devices and databases are created from master. go sends the batch.
3–6disk init creates two device files: 1 GB for data, 512 MB for the log.
7create database phoenix_test on phoenix_data = '1G' log on phoenix_log = '512M': data and log on separate devices. A separate log device is what makes "free log pages" a meaningful metric for the CDC backlog.
9–12select into (allows minimally logged select into/bcp in this test DB) and ddl in tran (allows create table inside transactions). Test conveniences; check the production database's own options.
13–14trunc log on chkpt: ASE truncates the log at each checkpoint, but never beyond the RepAgent secondary truncation point, so un-replicated records stay (test 7). Production databases normally keep this off and rely on dump transaction for point-in-time recovery; RepAgent's truncation point also holds dump tran back. Do not change production backup settings for CDC.

sybase/01_setup.sql

2sp_configure 'enable rep agent threads', 1: server-wide switch allowing RepAgent threads (dynamic, no restart). On this Developer Edition it needed no additional licence; for production licensing see licensing.
4–13The test table. payment_id numeric(18,0) identity primary key: auto-numbered key; the primary key is what RepAgent flags (G) and what becomes the Kafka key. Every captured table should have a primary key.
14sp_setreptable payment, true: marks the table for replication; ASE then writes the extra log information RepAgent needs and RepAgent forwards its changes. The first time, ASE warned Msg 9137 … LTM trunc. point not yet established, which is expected until RepAgent is enabled. Verify with sp_setreptable payment → true, owner_off, primary key = ….
16Print the version into the container log.

sybase/02_repagent.sql

4–7sp_config_rep_agent phoenix_test, 'enable', 'CDC_RS', 'rs_user', 'rs_password', run inside the database (from master it fails with Msg 18381). Enables RepAgent for the database, names the "Replication Server" to connect to (an interfaces entry) and the credentials it presents (rs_user/rs_password are local test values; in production the DBA uses values from the secret store, see security settings). It also establishes the secondary truncation point: from now on the log is held until RepAgent has delivered it.
8Show RepAgent status (not started yet).
12'net password encryption', 'false': send the password in the plain TDS login field, which the connector can check (history 4). Takes effect at the next RepAgent start.

sybase/03_log_threshold.sql

Creates table cdc_log_alert, procedure sp_cdc_log_alert and a free-space threshold on logsegment at 24,576 pages (75% free of 32,768). When free pages fall below it, ASE calls the procedure, which inserts a row and prints CDC ALERT: … into the errorlog. It never truncates anything. ASE's built-in "last-chance threshold" (288 pages here) remains; when reached, ASE suspends transactions that need log space until space is freed. Verified in test 7.

Test schema and data

Besides payment, discovery tables exercise every type: sybase/90_ltl_types_probe.sql.manual (ltl_types: all common types, update, delete, rollback, multi-row), 91_ltl_long_values.sql.manual (ltl_long composite key, 63/64/5,000-character values; ltl_nopk without key), 92_ltl_long_binary.sql.manual (ltl_long3, 3-digit lengths). Run manually: docker exec cdc-sybase bash -c 'source /opt/sybase/SYBASE.sh; isql -Usa -P… -SMYSYBASE -i /scripts/90_ltl_types_probe.sql.manual'. They are excluded by table.include.list=payment from Kafka but are visible to the probe.

Backup and restore considerations

  • RepAgent's secondary truncation point holds the log until delivery. A stopped connector therefore grows the log and can block dump tran from freeing space.
  • Loading a database dump or restarting from a restored database changes the log; OQIDs embed a database generation number, but restore scenarios were not tested. After any restore, plan a re-baseline (full snapshot) of downstream consumers.
  • dbcc settrunc('ltm', 'ignore') removes the truncation point and lets ASE free the log, discarding un-replicated changes for CDC. It is an emergency DBA action only, never automated (runbook).

Licensing and support facts

  • The local image is ASE Developer Edition (SySAM edition DE, licence type DT): for development and testing only. Do not redistribute the image.
  • Whether production RepAgent use requires an additional SAP licence option is not established by this project (SAP knowledge-base articles list separate SySAM features for replication products; none was required on Developer Edition). Action: confirm with the bank's SAP licence owner before go-live.
  • SAP documents LTL only up to version 700 and does not support third-party Replication Server emulation. Treat the protocol layer as unsupported by SAP.
