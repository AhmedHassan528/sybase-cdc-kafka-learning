Purpose: where each piece runs in production. ASE (SLES 12, outside the cluster) → bank network/firewall → LoadBalancer Service :11752 → the single Connect pod (dedicated KafkaConnect cluster, replicas: 1) → Event Streams brokers over TLS. The NetworkPolicy admits only the ASE host on 11752. Secrets come from the bank's secret store.

Why one replica: RepAgent connects to one host:port, and only the worker running the task has the listener open. With more replicas the Service would send RepAgent to workers without a listener. High availability comes from the pod being rescheduled (seconds to minutes) while ASE holds the log.

Does not show: the image registry and CI pipeline.

Prerequisites and questions for the platform team

  • Event Streams version and its Kafka version (compile/test against the same Connect API; 0.1.0 targets 3.8.0).
  • Namespace (cdc in the templates), permission to create KafkaConnect/KafkaConnector, Service of type LoadBalancer (MetalLB or cloud LB) or NodePort, NetworkPolicy, Secret.
  • An approved registry and an artifact repository for the JAR.
  • A Kafka user for Connect with: read/write on its three internal topics, write/describe on <prefix>.*, group sybase-cdc-connect.
  • Network path ASE host → LB address :11752 (firewall change) and the reverse path is not needed.
  • Production ASE facts from the DBA: @@servername, database name, charset (sp_helpsort), tables in scope and their primary keys, log size and current free space, RepAgent licence/option (licensing).

Building the worker image for Event Streams

Two options, both in deploy/openshift/02-kafkaconnect-eventstreams.yaml:

  1. Operator build (spec.build): the operator downloads the JAR from url, checks sha512sum, builds an image and pushes it to output.image. Needs a registry push secret. Compute the checksum with sha512sum sybase-cdc-connector-0.1.0.jar.
  2. Pre-built image: IBM's documentation describes a Dockerfile that starts FROM cp.icr.io/cp/ibm-eventstreams-kafka:<version>, copies plugins under /opt/kafka/plugins/ and sets USER 1001. For this connector: 
    FROM cp.icr.io/cp/ibm-eventstreams-kafka:<your Event Streams version>
COPY plugins/sybase-cdc/sybase-cdc-connector-0.1.0.jar /opt/kafka/plugins/sybase-cdc/
USER 1001
    Pulling from cp.icr.io needs an IBM entitlement key (obtain through the bank's IBM account; never put it in Git). Reference the image by digest in the KafkaConnect CR.

The local image sybase-cdc-connect:0.1.0 (based on apache/kafka) and its archive deliverables/images/sybase-cdc-connect-0.1.0.tar.gz are for Path A and for plain Strimzi-style clusters; Event Streams expects its own base image.

The externalConfiguration field follows the Event Streams 11.x documentation; newer Strimzi-based operators replace it with template volumes. Check the documentation of your exact version.

Deployment procedure (proposed)

  1. Prepare: answers to the prerequisites; change tickets for ASE (RepAgent, interfaces entry), firewall and OpenShift.
  2. Publish the artifact: upload the JAR (record SHA-256 and SHA-512) or push the image.
  3. Dry-run: oc apply --dry-run=server -f deploy/openshift/ after replacing placeholders (keep secrets out of the files).
  4. Create Secret, KafkaConnect; wait: oc get kafkaconnect sybase-cdc -n cdc -w until Ready; oc logs the pod; check /connector-plugins with oc exec … curl -s localhost:8083/connector-plugins.
  5. Create Service and NetworkPolicy; note the external address: oc get svc sybase-cdc-ltl -n cdc.
  6. Create the KafkaConnector; check oc get kafkaconnector sybase-cdc-phoenix -n cdc -o yaml status and the log line LTL server listening on 0.0.0.0:11752.
  7. Test connectivity from the ASE host to <lb>:11752 (TCP only).
  8. DBA configures ASE (in a change window): interfaces entry CDC_RS → <lb> 11752; sp_config_rep_agent db, 'enable', 'CDC_RS', user, password; net password encryption false; retry timeout 10; sp_setreptable for each table; log threshold. Note: enabling RepAgent creates the secondary truncation point; from then on the log is held until the connector acknowledges.
  9. Start RepAgent: sp_start_rep_agent db; verify in the connector log (RepAgent connected, using 760 or the version SP04 proposes).
  10. Smoke test with a test row agreed with the business, then the walkthrough checks (offsets, truncation point).

Rollback and upgrade: see deploy/rollback runbook.

If the platform is Confluent instead

The connector is a standard Kafka Connect plugin and does not depend on Event Streams. On Confluent for Kubernetes the equivalents are the Connect and Connector custom resources (API group platform.confluent.io); on plain Strimzi, kafka.strimzi.io KafkaConnect/KafkaConnector, which Event Streams' CRs mirror. The same rules apply: one replica (or a dedicated single-task cluster), a TCP Service, a Secret through a config provider. Not tested on either.

Monitoring to set up

  • Task state ≠ RUNNING (operator status or Connect REST) → page on-call.
  • ASE log free space and the existing threshold alert (cdc_log_alert table / errorlog text CDC ALERT).
  • RepAgent state from sp_help_rep_agent (down = not replicating, the log keeps growing).
  • Latency: ts_ms minus source.commit_time in a consumer, or Connect's source-record-poll-rate JMX metrics.
  • Pod restarts and heap usage (JMX).
