Maven build and JAR packaging

Maven is Java's standard build tool: it reads pom.xml, downloads declared dependencies from Maven Central, compiles, runs tests and packages a JAR (a zip of compiled classes). This project runs Maven inside a container (maven:3.9-eclipse-temurin-17), so no Java or Maven is installed on the host.

Purpose: every transformation between the source files and the class the worker finally loads. Key facts: the compile target is Java 17; Kafka Connect API and SLF4J are provided by the worker, so they are deliberately not inside the JAR (bundling them can cause class-loading conflicts); the connector has no other runtime dependency, so the shade step produces a JAR byte-identical to the plain one (same SHA-256).

Does not show: the Maven download cache (Docker volume cdc-m2-cache).

pom.xml, explained

1–5XML header and POM model version 4.0.0 (the only one Maven uses).
7–10Coordinates: groupId com.phoenix.cdc, artifactId sybase-cdc-connector, version 0.1.0 → JAR name sybase-cdc-connector-0.1.0.jar. Keep the version equal to SybaseCdcSourceConnector.VERSION.
12–16maven.compiler.release=17: compile against the Java 17 API and emit class version 61 (prevents accidental use of newer APIs). UTF-8 sources. kafka.version property reused below.
20–25connect-api 3.8.0, scope provided: available at compile time, not packaged; the worker supplies it at runtime. Its transitive dependency kafka-clients (with RecordMetadata, ConfigDef) comes along the same way.
26–31slf4j-api 1.7.36, provided (the worker ships the same version, verified in 04-kafka-java.txt).
32–37JUnit 5.10.2, scope test: only on the test classpath.
42–45Surefire 3.2.5: runs the JUnit 5 tests during mvn package.
46–60Shade 3.5.3 bound to package: merges runtime dependencies into one JAR. With none today it is a no-op; it is kept so that a future dependency is bundled automatically. createDependencyReducedPom=false avoids writing a modified POM next to the project.

Not pinned: maven-compiler-plugin and maven-jar-plugin versions come from Maven 3.9.16's defaults. For reproducible CI builds, pin them and the Maven image digest.

Build commands

  1. Build, test, copy to the plugin folder (what build.sh does): 
    ./sybase-cdc-connector/build.sh            # add -DskipTests to skip tests (not recommended)
    Inside, it runs docker run --rm -v "$SRC:/src" -v cdc-m2-cache:/root/.m2 -w /src maven:3.9-eclipse-temurin-17 mvn -B -q package: --rm deletes the container afterwards, the first -v mounts the project, the second keeps downloaded dependencies between builds, -B batch mode, -q quiet (only errors). Then it copies target/sybase-cdc-connector-0.1.0.jar to plugins/sybase-cdc/.
    Expected: a listing of plugins/sybase-cdc with a ~66 KB JAR and no ERROR lines. A test failure prints [ERROR] Tests run: …, Failures: 1 and stops.
  2. Run only the tests, verbosely: 
    docker run --rm -v "$(pwd -W)/sybase-cdc-connector:/src" -v cdc-m2-cache:/root/.m2 -w /src maven:3.9-eclipse-temurin-17 mvn -B test
    Expected (evidence tests/unit-tests.txt): Tests run: 11, Failures: 0, Errors: 0, Skipped: 0 and BUILD SUCCESS.
  3. Clean build (removes target/ first): add clean before package: … mvn -B clean package.
  4. Inspect and fingerprint the artifact: 
    unzip -l plugins/sybase-cdc/sybase-cdc-connector-0.1.0.jar      # 51 entries, 33 classes
unzip -p plugins/sybase-cdc/sybase-cdc-connector-0.1.0.jar META-INF/services/org.apache.kafka.connect.source.SourceConnector
sha256sum plugins/sybase-cdc/sybase-cdc-connector-0.1.0.jar
    Expected: the services file contains com.phoenix.cdc.sybase.connect.SybaseCdcSourceConnector; SHA-256 7e1e5bc225e035a79c925612c22ca2fb3cc34172e1c9a8a301566f0726b3f61b for the tested build. A different hash after rebuilding is normal (timestamps in the JAR) unless you pin the build environment; record it in the release.
  5. Install and reload: ./sybase-cdc-connector/deploy-local.sh = build + docker restart cdc-connect + wait until the task is RUNNING. The worker scans the plugin path only at start-up, so a restart is required after replacing the JAR.

Plugin layout and class loading

Kafka Connect gives each sub-folder of plugin.path its own class loader, so plugins cannot see each other's libraries and their libraries do not clash with the worker's. Layout used: /opt/connectors/sybase-cdc/sybase-cdc-connector-0.1.0.jar. If the connector ever needs a third-party library (for example an Avro serializer), either shade it into the JAR or put its JAR in the same folder; never put it on the worker's own classpath. Discovery works through the META-INF/services file (Java ServiceLoader), which is how Connect 3.6+ can scan plugins quickly.

Tutorial: creating a source connector from an empty folder

This tutorial reproduces the structure of the real connector. Steps 1–8 give a working but trivial connector; steps 9–12 point to the real CDC code, which you should copy rather than retype. The skeleton in step 6 is a teaching example, not the production implementation.

  1. JDK and Maven: nothing to install if you use the Maven container (docker pull maven:3.9-eclipse-temurin-17). Otherwise install a JDK 17+ (e.g. Eclipse Temurin) and Maven 3.9+, then check java -version and mvn -v.
  2. Project folders: my-connector/pom.xml, src/main/java/<package path>/, src/main/resources/META-INF/services/, src/test/java/.
  3. Kafka Connect API version: use the same version as the target worker (here 3.8.0; on OpenShift, the Kafka version of your Event Streams or Confluent release). Compiling against an older API than the runtime is safe; newer is not.
  4. Dependencies: copy lines 12–38 of the project's pom.xml (provided scope for connect-api and slf4j-api).
  5. Service file: src/main/resources/META-INF/services/org.apache.kafka.connect.source.SourceConnector containing the fully qualified connector class name.
  6. Connector and task classes (teaching skeleton): 
    // HelloConnector.java
package hello;
import java.util.*;
import org.apache.kafka.common.config.ConfigDef;
import org.apache.kafka.connect.connector.Task;
import org.apache.kafka.connect.source.SourceConnector;

public class HelloConnector extends SourceConnector {
    private Map<String, String> props;
    @Override public void start(Map<String, String> p) { props = p; }
    @Override public Class<? extends Task> taskClass() { return HelloTask.class; }
    @Override public List<Map<String, String>> taskConfigs(int max) { return List.of(props); }
    @Override public void stop() { }
    @Override public ConfigDef config() { return new ConfigDef().define("topic", ConfigDef.Type.STRING, ConfigDef.Importance.HIGH, "Target topic"); }
    @Override public String version() { return "0.0.1"; }
}

// HelloTask.java
package hello;
import java.util.*;
import org.apache.kafka.connect.source.SourceRecord;
import org.apache.kafka.connect.source.SourceTask;

public class HelloTask extends SourceTask {
    private String topic; private long n;
    @Override public void start(Map<String, String> p) { topic = p.get("topic"); }
    @Override public List<SourceRecord> poll() throws InterruptedException {
        Thread.sleep(1000);
        return List.of(new SourceRecord(Map.of("source", "hello"), Map.of("n", n), topic, null, "hello " + n++));
    }
    @Override public void stop() { }
    @Override public String version() { return "0.0.1"; }
}
    Verified: these two files plus the service file compile with the project's POM settings (mvn package produced a 4 KB JAR). They were not deployed to a worker.
  7. Configuration definition: move settings into a class extending AbstractConfig with a ConfigDef (see SybaseCdcConfig), so invalid configs fail at start().
  8. Build, install, register: mvn package, copy the JAR into a new folder under plugin.path, restart the worker, check GET /connector-plugins, then POST /connectors with {"name":"hello","config":{"connector.class":"…HelloConnector","topic":"hello"}} and read the topic.
  9. Offsets and recovery: make the source offset describe a position you can resume from; read it in start() with context.offsetStorageReader().offset(partition); use a partition map with a stable key order (a lesson from history 7.3); only claim a position once everything before it is acknowledged (Figure 17).
  10. Error handling and resources: throw ConnectException for fatal start-up errors; close sockets and threads in stop(); never block poll() forever.
  11. The real CDC layer: copy the tds, ltl and cdc packages unchanged; they have no Kafka dependency. Wire them as SybaseCdcSourceTask does: an LtlServer with a listener that feeds a TransactionBuffer, a bounded queue drained by poll(), and an AckTracker fed by commitRecord().
  12. Tests: unit tests with captured LTL fixtures (LtlParserTest); end-to-end tests with the Docker environment and the scenario scripts (test chapter).
