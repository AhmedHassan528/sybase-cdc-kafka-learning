Local reproduction: step-by-step walkthrough

These 28 steps rebuild the whole local environment from the project folder and prove it works end to end. They follow the order that was actually used, including the manual steps the scripts do not perform (history 7.6). Each step says where it runs: HOST = a Git Bash / Linux shell on your PC in the project folder; CONTAINER = inside a container; SQL = an ASE isql session.

Purpose: the loop a developer goes through: edit code → build in the Maven container → copy to the plugin folder → restart the worker → generate ASE changes → read Kafka → compare. The left column is one-time setup (steps 1–17 below); the right column is the edit/test loop (steps 18–26).

Does not show: the performance and failure tests, which are in the test chapter.
Credentials in this walkthrough The local environment uses fixed local test values from the public datagrip/sybase image and from sybase/02_repagent.sql. They protect nothing and must never be reused anywhere else. The commands below refer to them as ${SYBASE_PASSWORD} (ASE sa) and ${LTL_PASSWORD} (RepAgent → connector). Set them once per shell from the project files, so they are not typed into your shell history: 
export SYBASE_PASSWORD="$(sed -n 's/^ *SYBASE_PASSWORD: *//p' docker-compose.yml)"
export LTL_PASSWORD="$(sed -n "s/.*'enable', 'CDC_RS', 'rs_user', '\([^']*\)'.*/\1/p" sybase/02_repagent.sql)"
The helper scripts in captures/ contain the same local values in clear text; that is acceptable only because they are local test values.

A. Prerequisites (steps 1–4)

  1. HOSTDocker. Purpose: everything runs in containers. Command: docker version and docker compose version.
    Expected: both client and server versions print (tested: engine and client 29.6.1, Docker Compose v5.3.0; evidence/01-tooling.txt). Error: Cannot connect to the Docker daemon → start Docker Desktop.
  2. HOSTResources. Docker Desktop needs about 6 GB RAM for the four containers (Connect alone peaked at 1.95 GiB in test 6) and about 10 GB of free disk (image sizes from evidence/02-images.txt: ASE 3.3 GB, Kafka 0.2 GB shared by two containers, Kafka UI 0.15 GB, Maven 0.23 GB, plus the ASE devices and Kafka data inside the containers). Check with docker info --format '{{.MemTotal}}'.
  3. HOSTShell. On Windows use Git Bash. The helper scripts set MSYS_NO_PATHCONV=1 so that paths like /opt/kafka are not rewritten to C:/Program Files/Git/opt/kafka. Symptom if forgotten: No such file or directory for a path that exists inside the container.
  4. HOSTProject folder. Confirm the expected files: ls docker-compose.yml connect-distributed.properties sybase/ connectors/ plugins/ sybase-cdc-connector/. The full list is in the file inventory.

B. Build the connector (steps 5–7)

  1. HOSTBuild and unit-test. ./sybase-cdc-connector/build.sh. Purpose: compile, run the 11 unit tests, copy the JAR to plugins/sybase-cdc/. First run downloads Maven dependencies (a few minutes). Expected: no [ERROR] lines; details in Build commands.
  2. HOSTVerify the artifact. ls -l plugins/sybase-cdc/ && sha256sum plugins/sybase-cdc/*.jar. Expected: one JAR of about 66 KB. Record the hash.
  3. HOST(Optional) Build the shim. sybase/rie_shim.so is already built. Rebuild only if you changed rie_shim.c (command in the shim section).

C. Start the environment (steps 8–13)

  1. HOSTStart. docker compose up -d. Purpose: pull images on first run, create the network …_default, start the four containers. Compose waits for the Kafka health check before starting Connect.
    Expected: four Started/Healthy lines. Error: port is already allocated → another program uses 5000, 8080, 8083, 11752 or 29092; stop it or change the left side of the port mapping.
  2. HOSTWatch ASE initialise. docker logs -f cdc-sybase (Ctrl+C to stop following).
    Expected, first boot: Waiting for ASE to accept logins..., SYBASE STARTED, INIT (first boot), one --> /scripts/0N_*.sql line per script, then READY. Creating the 1 GB + 512 MB devices takes a minute or two. Error: dataserver died; tail of errorlog followed by Snap::Validate → the kernel workaround is not active (check security_opt and the LD_PRELOAD line, troubleshooting).
  3. HOSTCheck containers. docker ps --format '{{.Names}} | {{.Status}}'.
    Expected (from evidence/03-containers.txt): cdc-connect | Up …, cdc-kafka | Up … (healthy), cdc-kafka-ui | Up …, cdc-sybase | Up ….
  4. HOSTCheck the worker and the plugin. 
    curl -s localhost:8083/
curl -s localhost:8083/connector-plugins
    Expected: {"version":"3.8.0",…}, and a plugin list that contains {"class":"com.phoenix.cdc.sybase.connect.SybaseCdcSourceConnector","type":"source","version":"0.1.0"}. Missing plugin: the JAR was not in plugins/sybase-cdc/ when the worker started → step 5, then docker restart cdc-connect.
  5. SQLCheck ASE. echo -e "select @@servername, @@version\ngo" | captures/isql.sh.
    Expected: MYSYBASE and Adaptive Server Enterprise/16.0 SP02 PL02/… (evidence/08-ase-facts.txt).
  6. SQLCheck the RepAgent configuration made by the init scripts. echo -e "sp_help_rep_agent phoenix_test, 'config'\ngo" | captures/isql.sh.
    Expected: rs servername = CDC_RS, rs username = rs_user, net password encryption = false. Also check the interfaces entry: docker exec cdc-sybase grep -A2 CDC_RS /opt/sybase/interfaces → two lines tcp ether connect 11752.

D. Create the connector and start RepAgent (steps 14–17)

  1. HOSTCreate the connector. Purpose: start the task, which opens port 11752. 
    curl -s -X POST -H 'Content-Type: application/json' --data @connectors/sybase-cdc-phoenix.json localhost:8083/connectors
    Expected: the configuration echoed back with "tasks":[] or [{"connector":"sybase-cdc-phoenix","task":0}]. Note: the echo contains the LTL password in clear text, one reason production must use a config-provider reference (security settings). Error: 409 Conflict → it exists already; use PUT /connectors/sybase-cdc-phoenix/config with only the inner config object.
  2. HOSTConfirm RUNNING and listening. 
    curl -s localhost:8083/connectors/sybase-cdc-phoenix/status
docker logs cdc-connect 2>&1 | grep -E "Starting Sybase CDC task|LTL server listening" | tail -3
    Expected: connector and task "state":"RUNNING"; log lines Starting Sybase CDC task for MYSYBASE.phoenix_test; last committed OQID in Kafka: none (first start) and LTL server listening on 0.0.0.0:11752.
  3. SQLShorten RepAgent's retry timeout (manual, once). echo -e "sp_config_rep_agent phoenix_test, 'retry timeout', '10'\ngo" | captures/isql.sh. Purpose: after a connector restart RepAgent retries every 10 s instead of 60 s. Takes effect at the next RepAgent start.
  4. SQLStart RepAgent (manual, first time only; later boots start it automatically). echo -e "sp_start_rep_agent phoenix_test\ngo" | captures/isql.sh.
    Expected: in the Connect log within a few seconds: RepAgent connected from /172.x.x.x:… and connect source MYSYBASE.phoenix_test proposed LTL 760 -> using 760. Error: ASE errorlog Login failed for user 'rs_user' → user/password mismatch or net password encryption still true (troubleshooting). Order matters: start RepAgent only after step 15; otherwise it fails to connect and keeps retrying.

E. Verify end to end (steps 18–24)

  1. SQLRepAgent status. echo -e "sp_help_rep_agent phoenix_test, 'process'\ngo" | captures/isql.sh. Expected: a row for phoenix_test whose state is sleeping when idle or scanning while reading the log (values recorded every 5 s in test 6, evidence/tests/t6-run2-monitor.csv).
  2. SQLInsert a row (test 1 pattern): 
    insert payment (account_no, amount, currency) values ('WT-ACC', 100.00, 'EGP')
go
    Run it with captures/isql.sh (paste the two lines into its standard input).
  3. HOSTRead Kafka. captures/consume.sh sybase.phoenix_test.payment 8000 | grep WT-ACC.
    Expected: one line {"payment_id":"…"} | {"op":"c","before":null,"after":{… "account_no":"WT-ACC","amount":"100",…},"source":{… "table":"payment",… "seq":0,"txn_rows":1},…}. The shape matches the real test 1 record in the Kafka chapter.
  4. SQLUpdate and delete, then a rollback. update payment set amount = 175.25 where account_no = 'WT-ACC', then delete payment where account_no = 'WT-ACC', then begin tran insert payment … rollback. Expected in Kafka: one "op":"u" (with before and after), one "op":"d" (with before, after null), and nothing for the rolled-back insert.
  5. HOSTKafka UI. Open http://localhost:8080 → Topics → sybase.phoenix_test.payment → Messages. Purpose: the same records, browsable. Kafka Connect → sybase-cdc-phoenix shows the task state.
  6. HOSTOffsets advance. After 5–10 s: docker logs cdc-connect 2>&1 | grep "Committing offsets" | tail -1. Expected: Committing offsets for N acknowledged messages. Read the stored position from the internal topic (the REST /offsets view can be stale, see why): 
    MSYS_NO_PATHCONV=1 docker exec cdc-kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 \
  --topic _connect-offsets --from-beginning --timeout-ms 5000 --property print.key=true 2>/dev/null | tail -1
  7. SQLASE log is released. captures/isql.sh < captures/truncpage.sql (read-only: select page from master..syslogshold where name like '%replication_truncation%'). Expected: the secondary truncation page moves forward after the connector acknowledges; log usage stays low. If the page never moves, see the log runbook before doing anything else.

F. Development loop (step 25)

  1. HOSTChange, rebuild, reload. After editing Java code: ./sybase-cdc-connector/deploy-local.sh (build + docker restart cdc-connect + wait for RUNNING). RepAgent reconnects by itself within the retry timeout; the task resumes from its stored offset. Re-run steps 19–23.

G. Stop, clean up, reset (steps 26–28)

  1. HOSTPause the environment, keeping all data. docker compose stop, later docker compose start. ASE shuts down cleanly (the trap in start.sh), RepAgent restarts automatically at the next boot. While the connector is down, ASE keeps the unreplicated log; a long stop with write activity fills the log (test 7 measured this).
  2. HOSTRemove the connector only. curl -s -X DELETE localhost:8083/connectors/sybase-cdc-phoenix. Its stored offset remains in _connect-offsets; creating it again with the same name and database.* values resumes from there. RepAgent stays configured and keeps holding the log until a connector listens again, so also run sp_stop_rep_agent phoenix_test if you stop for long.
  3. HOSTFull reset.
    DESTRUCTIVE: deletes all local data docker compose down removes the containers. Because no named volume is used, this erases the ASE database phoenix_test and all Kafka topics and offsets. The next up re-runs the init scripts and steps 14–17 are needed again. Do this only on the local test environment, never against shared or production systems. To keep data, use step 26 instead.
    # DESTRUCTIVE (local only): containers, ASE database and Kafka data are deleted
docker compose down
    docker compose down does not delete images or the Maven cache volume cdc-m2-cache.
