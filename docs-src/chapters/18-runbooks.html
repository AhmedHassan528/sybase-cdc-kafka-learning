Operational runbooks

Each runbook lists who runs it, preconditions, steps, verification and rollback. Commands are shown for the local environment and, where different, for OpenShift. None of these runbooks was executed end to end as a runbook; their steps reuse operations that were exercised in the tests (named in each one). Placeholders: <db> database, <ns> namespace, ${…} secrets.

RB-1 Daily health check (read-only)

  1. Task RUNNING: curl -s localhost:8083/connectors/sybase-cdc-phoenix/status · oc get kafkaconnector sybase-cdc-phoenix -n <ns>.
  2. RepAgent up: sp_help_rep_agent <db>, 'process' → sleeping or scanning.
  3. Log space: select lct_admin('logsegment_freepages', db_id('<db>')); any rows in cdc_log_alert since yesterday?
  4. Positions move: truncation page (captures/truncpage.sql) is higher than yesterday's if there was activity.
  5. Worker log has no ERROR for the connector.

All queries are read-only. Used throughout test 6 monitoring.

RB-2 Planned stop and start

Precondition: the stop window is short compared with the time the log takes to fill at current write rate (test 7: ≈ 655 pages per 100,000 rows; size this for production).

  1. Stop the connector: curl -s -X PUT localhost:8083/connectors/sybase-cdc-phoenix/stop (Kafka 3.5+; closes port 11752). On OpenShift: spec.state: stopped in the KafkaConnector if your operator version supports it, otherwise scale as agreed with the platform team.
  2. RepAgent notices and retries every retry timeout seconds; nothing to do on ASE for short stops. For long stops, a DBA may run sp_stop_rep_agent <db> (the log is held either way).
  3. Start: curl -s -X PUT localhost:8083/connectors/sybase-cdc-phoenix/resume; if RepAgent was stopped, sp_start_rep_agent <db>.
  4. Verify: RepAgent connected in the log; truncation page advances; consumers see new events.

Exercised in T6a (stop/resume during a 20,000-transaction load: 0 lost, 0 duplicates).

RB-3 Restart a FAILED task

  1. Read the reason: …/status → tasks[0].trace. Do not restart in a loop without reading it.
  2. If the cause is fixed or transient: curl -s -X POST localhost:8083/connectors/sybase-cdc-phoenix/tasks/0/restart.
  3. If it is a parse error (unknown LTL), restarting repeats it: RepAgent resends the same transaction. Capture it (what to collect), fix the parser, redeploy (RB-4). The log keeps growing meanwhile: watch RB-6 thresholds.

RB-4 Deploy a new connector version, and roll back

Purpose: the safe order for changing the connector: build and test → publish artifact with checksum → stop connector → replace image/JAR → start → verify → keep the previous artifact for rollback. Offsets survive because the connector name and {database, server} stay the same.

Rollback rule: rolling back the JAR is safe as long as the offset format is unchanged ({commit_oqid} in 0.1.0). If a future version changes the offset format, its release notes must say so.
  1. Build and run unit tests; record SHA-256/SHA-512.
  2. Local: ./sybase-cdc-connector/deploy-local.sh (build, restart worker, wait RUNNING). OpenShift: update build.plugins[].artifacts[].url + sha512sum, or the image digest, in the KafkaConnect CR; the operator rolls the pod.
  3. Verify: plugin version in /connector-plugins; task RUNNING; last committed OQID in Kafka: <hex> (not none) in the start log; walkthrough checks.
  4. Rollback: put the previous artifact/digest back and repeat step 2.

The restart part was exercised repeatedly during development (deploy-local.sh) and in T4b/T6b (resume from stored offset).

RB-5 Rotate the RepAgent ↔ connector password

Proposed, not tested. Both sides must change in one window.

  1. DBA: sp_stop_rep_agent <db>.
  2. DBA: sp_config_rep_agent <db>, 'rs password', '${NEW_LTL_PASSWORD}' (from the secret store; check the exact parameter name on SP04 with sp_config_rep_agent <db>).
  3. Platform: update the Secret; restart the task so the config provider re-reads it.
  4. DBA: sp_start_rep_agent <db>. Verify: RepAgent connected, no Msg 4002 in the errorlog.
  5. Rollback: the old password in both places.

RB-6 Add a table to capture

  1. Confirm the table has a primary key and supported column types (no LOB).
  2. Kafka: create topic <prefix>.<db>.<table> with the agreed partitions/RF; grant ACLs.
  3. Connector: add the table to table.include.list (CR or REST PUT …/config); the task restarts.
  4. DBA: sp_setreptable <table>, true. Only changes after this point are captured; existing rows need a separate initial load (not part of this connector).
  5. Verify with a test change agreed with the table owner.

RB-7 Transaction log filling up because the connector is not acknowledging

Read completely before actingThe secondary truncation point protects changes that have not reached Kafka. Removing it frees the log but permanently loses those changes for Kafka and requires a re-baseline of every consumer. That decision belongs to the DBA team and the data owners, not to an operator following a runbook.

Trigger: CDC ALERT in the ASE errorlog / row in cdc_log_alert / free log pages falling.

  1. Measure (read-only): free pages now and 5 minutes later → time until full. Check master..syslogshold (is the oldest hold the replication truncation point, or an open user transaction?).
  2. Restore delivery first (the normal fix; drains on its own, test 7 drained 1.05M rows in 99 s): task state (RB-3), RepAgent state (sp_start_rep_agent if down), network, Kafka.
  3. Buy time without losing data: the DBA can add log space (alter database <db> log on <device> = '<size>') according to the bank's standards.
  4. Only if the above fails and the business accepts data loss for Kafka:
    DESTRUCTIVE: manual DBA decision only. Never automated, never run during the tests of this project. 
    -- DESTRUCTIVE: discards the replication truncation point. Changes not yet in Kafka are lost for CDC.
-- Run only with written approval of the DBA lead and data owner. Then re-baseline all consumers.
sp_stop_rep_agent <db>
go
use <db>
go
dbcc settrunc('ltm', 'ignore')
go
dump transaction <db> ... -- per the bank's log backup procedure (do not use 'truncate_only' without DBA approval)
go
    Afterwards, re-enable with dbcc settrunc('ltm', 'valid'), reset the connector position (new connector name, or delete its offset), restart RepAgent and run an initial load or reconciliation for every consumer.
  5. Post-incident: root cause, how long the connector was down, whether alert thresholds were early enough.

Steps 1–2 were exercised in test 7 (alert fired at 25.4% used; no suspended processes; full drain). Steps 3–4 were deliberately not run.

RB-8 Decommission CDC for a database

  1. Stop consumers' dependency (agreed date).
  2. DBA: sp_stop_rep_agent <db>, then sp_config_rep_agent <db>, 'disable' (removes the secondary truncation point so the log is no longer held), sp_setreptable <table>, false.
  3. Delete the KafkaConnector (or DELETE /connectors/…), then the KafkaConnect cluster, Service, NetworkPolicy, Secret.
  4. Topics: keep or delete according to the retention policy; deleting topics is irreversible.
