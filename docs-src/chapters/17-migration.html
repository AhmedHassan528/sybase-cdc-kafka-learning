Version compatibility and migration to ASE 16.0 SP04 PL07

The connector was built and tested against ASE 16.0 SP02 PL02. Production is ASE 16.0 SP04 PL07 HF1 (EBF 31179), SLES 12.4. Nothing in this project proves that SP04's RepAgent sends the same bytes. This chapter lists what could differ and a safe procedure to find out.

What could differ on SP04

  • Proposed LTL version above 760, and whether RepAgent accepts the connector's answer 760.
  • New or changed commands/keywords in distribute (for example for new data types or features enabled on the server).
  • Login packet: capabilities, packet size, password encryption defaults.
  • Configured features on the production server: stream replication, multithread rep agent, send structured oqids, short ltl keywords; the connector supports only the defaults (all false).
  • Column types used by Phoenix tables that the payment test never exercised.

Validation procedure (non-production SP04 server)

Never on the production databaseEnabling RepAgent creates a secondary truncation point that holds the log. Use a dedicated SP04 test server (same version and patch level as production, restored copy of the schema, masked data). The discovery probe acknowledges every transaction immediately and must never be pointed at a database whose changes matter.
  1. Environment: an SP04 PL07 HF1 test ASE; a Connect worker with the 0.1.0 JAR; network path ASE → worker:11752.
  2. Configure RepAgent exactly as production will be (settings), pointing at the worker.
  3. Capture raw messages: start the worker with the JVM property -Dltl.dump.dir=/tmp/ltl-dump (for example through KAFKA_OPTS) so every RepAgent message is saved as NNNNNN-type.bin, and set ltl.trace=true for the session. These files contain the test data: treat them as confidential.
  4. Generate coverage: run the type-probe scripts (sybase/90…92_*.sql.manual) and the Phoenix tables' DDL with representative rows: every column type, NULLs, max lengths, updates of PK and non-PK columns, deletes, rollbacks, multi-row transactions.
  5. Compare: the connect source line (proposed LTL N -> using 760), the login log lines and the dumped bytes with the SP02 captures in docs/evidence/ltl/. Any parse error makes the task FAILED with the offending text in the trace.
  6. Add fixtures: copy representative SP04 messages into the unit tests (as LtlParserTest does with SP02 captures) and run mvn test.
  7. Rerun the integration suite (T1–T7, P5, T6a/b) on SP04 with the same acceptance criteria and evidence.
  8. Record results in this handbook (version matrix + test report) before any production change ticket.

Upgrading components later

  • ASE patch: repeat the validation procedure; RepAgent must be stopped during ASE upgrade anyway.
  • Kafka / Event Streams: recompile against the new connect-api version, run unit tests, smoke test in the test namespace.
  • Connector: offsets are stored by connector name and {database, server}; keep both unchanged to resume where the previous version stopped (runbook).
