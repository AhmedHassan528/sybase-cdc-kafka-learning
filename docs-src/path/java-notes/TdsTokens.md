purpose
  The answers the connector sends back to RepAgent are TDS 5.0 token streams: small tagged records such as "login accepted", "here is a message", "here is a row" and "done". TdsTokens is a builder for such a stream. You call one method per token, in order, and then take the bytes with bytes(); every integer is written in the byte order the client asked for at login.

class: TdsTokens
  The builder. It collects the bytes of the tokens in an internal buffer and remembers the client's byte order and character set.

class: TdsTokens.Column
  A record that describes one column of a result set: its name, its wire data type and its maximum length. It is used by rowFormat and row.

class: TdsTokens.Buf
  A small private helper class (not static, so it can read the outer object's byte order). It writes 1, 2 and 4 byte integers and raw bytes in the right order. Keeping it as a class means the token methods read like a description of the record.

method: TdsTokens.<init>(ByteOrder,Charset)
  Remembers the byte order and the character set that the login negotiated; every later token uses them.

method: TdsTokens.loginAck(boolean,String,byte[])
  The LOGINACK token (0xAD): the answer to a login. It says whether the login succeeded (5) or failed (6), claims TDS version 5.0, and names the program (the connector pretends to be a server) and its version.

method: TdsTokens.raw(byte[])
  Appends bytes unchanged. It is used to echo the client's own capability token back, because that token carries its own length.

method: TdsTokens.envChange(int,String,String)
  The ENVCHANGE token (0xE3): "a session setting changed from X to Y". The handshake uses it to confirm the packet size.

method: TdsTokens.message(int,int,String,String)
  The EED token (0xE5): an extended message with a number, a severity, a text and the server name. A severity of 11 or more is an error to the client. The session uses it to refuse a login (message 4002) or a "connect source" request (message 32001) with a readable reason.

method: TdsTokens.rowFormat(List)
  The ROWFMT token (0xEE): describes the columns of the result set that follows. Some answers (for example the one to "get truncation") are tiny result sets.

method: TdsTokens.row(List,Object...)
  The ROW token (0xD1): writes one row. The values must match the declared columns: an Integer for an int column, a String for varchar, a byte array for varbinary; anything else is an error.

method: TdsTokens.done(int,int)
  The DONE token (0xFD) that closes a response, with a status and a row count. RepAgent expects exactly one DONE per message it sent.

method: TdsTokens.bytes()
  Returns everything written so far. The caller passes it to TdsChannel.sendResponse, which cuts it into packets.

method: TdsTokens.token(int,TdsTokens.Buf,boolean)
  Writes the framing every token shares: the token id, then the length of the body (2 or 4 bytes, depending on the token), then the body.

method: TdsTokens.Column.<init>(String,int,int)
  Stores the three fields of the record.

method: TdsTokens.Column.name()
  Accessor generated for the record component name.

method: TdsTokens.Column.type()
  Accessor generated for the record component type.

method: TdsTokens.Column.maxLen()
  Accessor generated for the record component maxLen.

method: TdsTokens.Column.toString()
  Generated by the compiler for the record.

method: TdsTokens.Column.hashCode()
  Generated by the compiler for the record; not used by the connector.

method: TdsTokens.Column.equals(Object)
  Generated by the compiler for the record; not used by the connector.

method: TdsTokens.Buf.<init>(TdsTokens)
  The constructor of the helper. The outer object is passed in implicitly so the helper can read its byte order.

method: TdsTokens.Buf.u8(int)
  Writes one byte.

method: TdsTokens.Buf.u16(int)
  Writes two bytes, little- or big-endian according to the negotiated order.

method: TdsTokens.Buf.u32(int)
  Writes four bytes, little- or big-endian according to the negotiated order.

method: TdsTokens.Buf.raw(byte[])
  Writes the given bytes unchanged.

method: TdsTokens.Buf.bytes()
  Returns the bytes written to this helper.

lines: 18-22
  The status bits of the DONE token. DONE_FINAL (0) ends a response, DONE_MORE says another result follows, DONE_ERROR marks a failure.

lines: 43-44
  The login answer states success as the code 5 and failure as 6, then four bytes for TDS version 5.0. Both numbers come from the TDS 5.0 definition that the code follows (see the comments in the file).

lines: 141-148
  The only place where the byte order matters. The same value is written low byte first or high byte first depending on what the client asked for at login.

design
  Every method returns the builder itself, so a response reads as a chain: loginAck, then the capability echo, then envChange, then done. This makes the order of tokens, which the client is strict about, visible in the code of the caller.

fits
  TdsTokens is used by LtlSession to build every answer (the login answer, the answers to RepAgent's questions, the acknowledgement of each batch). It writes integers in the byte order that the login record asked for, and the packet channel of the same package then sends the bytes.
