AckTracker.java

sybase-cdc-connector/src/main/java/com/phoenix/cdc/sybase/cdc/AckTracker.java · 68 lines · every non-blank line is annotated (checked by gen-source.js)

Role: converts Kafka's per-record acknowledgements into one safe log position, the watermark. The watermark is the commit OQID of the newest transaction such that it and every transaction before it is completely in Kafka. RepAgent receives this value in get truncation, so ASE only frees log space that Kafka holds. See diagram 17.

Threads: register() runs on the RepAgent session thread; ack() runs on the Kafka producer's callback thread; acked() runs on the session thread. All public methods are synchronized. Tests: AckTrackerTest (out-of-order acks, empty transaction). End-to-end evidence: test P5 (Kafka paused: watermark frozen, then advanced).

Nested static class Pending: one per transaction that was registered: its commit OQID and how many of its records are still unacknowledged. static means it does not hold a reference to the outer tracker. Lines 35–41

Register a transaction. Called in commit order, once per committed transaction that will be published, with the number of Kafka records it produces. A transaction with 0 records (e.g. it touched only tables excluded by table.include.list, or only DDL markers) is registered with 0 so that it can move the watermark too; otherwise ASE could never truncate past a long stretch of such transactions. advance() is called immediately because a 0-record transaction may already be complete. Returns the Pending so each Kafka record can carry a reference to it.

63    private void advance() {
64        while (!queue.isEmpty() && queue.peekFirst().remaining <= 0) {
65            acked = queue.pollFirst().oqid;
66        }
67    }
Lines 63–67

The watermark rule. While the oldest pending transaction has no unacknowledged records left, remove it and make its OQID the new watermark. The loop stops at the first transaction that is still waiting, even if later ones are complete. This is exactly the property that makes truncation safe. If changed (e.g. taking the maximum acknowledged OQID): a crash after T2 was acknowledged but before T1 was would release T1's log records and lose T1.
