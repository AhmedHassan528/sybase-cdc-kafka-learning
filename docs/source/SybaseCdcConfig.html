sybase-cdc-connector/src/main/java/com/phoenix/cdc/sybase/connect/SybaseCdcConfig.java · 95 lines · every non-blank line is annotated (checked by gen-source.js)

Role: declares every connector setting (name, type, default, validator, importance, help text) using Kafka's ConfigDef, and offers typed getters. Kafka Connect uses the same ConfigDef to validate a configuration (PUT /connector-plugins/.../config/validate) and to show settings in UIs. The full property reference is in the configuration chapter.

Security finding: Type.PASSWORD hides the value in logs ([hidden]), but Kafka Connect's REST API still returns the configuration as submitted. Use a config provider (file or Kubernetes secret) so the stored configuration only contains a reference.

84    /**
85     * Source partition for Kafka Connect offsets: one per ASE database.
86     * Connect finds stored offsets by the serialized bytes of this map, so its key order must be
87     * stable across JVM restarts: a TreeMap, never Map.of() (whose iteration order is randomized).
88     */
Lines 84–88

Comment recording a real defect found during testing: Kafka Connect looks up stored offsets by the serialized bytes of the partition map. Map.of() iterates in a different order in each JVM run, so after a restart the same partition serialized differently and the stored offset was not found (7 duplicates in tests 1 and 3).

89    public Map<String, String> sourcePartition() {
90        Map<String, String> p = new TreeMap<>();
91        p.put("server", serverName());
92        p.put("database", databaseName());
93        return p;
94    }
Lines 89–94

The fix: a TreeMap always iterates keys in sorted order (database, then server), so the bytes are stable. Evidence: after the fix the task logged the stored OQID on every restart (tests 4–7). Do not change the keys or their values in a running system; that would reset the connector's position.
