LtlLexer.java

sybase-cdc-connector/src/main/java/com/phoenix/cdc/sybase/ltl/LtlLexer.java · 123 lines · every non-blank line is annotated (checked by gen-source.js)

Role: splits one raw LTL 760 message (bytes) into tokens. A lexer (tokenizer) is the first stage of every parser: it turns a stream of characters into meaningful pieces (words, symbols, values) so the parser can reason about structure.

Why bytes, not text: LTL 760 length prefixes count bytes. With a multi-byte character set (UTF-8, or UTF-16 for univarchar), decoding first would make the lengths wrong. The lexer therefore works on byte[] and decoding happens later per value.

Source of truth for the encoding: captures of the real RepAgent (ASE 16.0 SP02 PL02), not SAP documentation (which stops at LTL 700). The marker table is in the RepAgent chapter. Known gaps: 4-digit lengths (values of 256 KB or more, i.e. text/image LOBs sent via rs_writetext) are not supported; the line 9 comment refers to a GUIDE.md that does not exist (this handbook replaces it).

Tests: all LtlParserTest cases run through this lexer with real captured messages.

Lines 52–62

How many length digits follow a marker. Learned from captures: char/varchar use ", #, 9 for 1, 2 and 3 digits (up to 63, 4,095 and 262,143 bytes); binary uses , - :; unichar uses 6 7 <. All other types (numbers, dates) always use one digit. Evidence: 63 vs 64 characters (~"` vs ~#"!), 5,000 characters (~9"/)), 5,000 binary bytes (~:"/)), 4,200 unicode bytes (~<""I). If ASE SP04 sends another marker, the token length would be misread and parsing fails loudly (the session drops the connection, nothing is acknowledged); add the marker here and a fixture test.
