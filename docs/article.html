1.Introduction

A payment lands in a database. A minute later, three other systems want to know about it: fraud detection, a reporting store, a notification service. You can ask the database every few seconds what changed (polling), or you can read the one place where the database already writes down every change: its transaction log. That second approach is change data capture, or CDC.

In this article I build a CDC pipeline from SAP/Sybase ASE to Apache Kafka, and I show you how to build it yourself. First we run a working pipeline on your own machine and watch real events appear. Then we rebuild the connector in six checkpoints, each with tests, so you see why every piece exists.

The path of one change

Here is the whole journey in five stops. We will meet each one again later with real commands and output.

  1. The application commits a row change. ASE writes it to its transaction log first, before it counts as durable.
  2. RepAgent reads the log. RepAgent is a thread inside ASE. It is built to feed a Replication Server, and it sends changes in a text-like format called LTL (Log Transfer Language) over the TDS protocol.
  3. Our connector pretends to be that Replication Server. We register a fake server name, CDC_RS, in the ASE interfaces file and point it at the connector's port 11752. RepAgent connects, logs in, and streams LTL to us. No real Replication Server is involved.
  4. The connector holds rows until COMMIT. RepAgent forwards changes of transactions that are still open, and even of ones that later roll back (a raw capture from the original project shows a rolled-back insert being sent, and the lab's rollback test shows that nothing reaches Kafka: evidence/23). The connector buffers them and publishes a transaction only when its commit arrives.
  5. Kafka stores the events, then we acknowledge. Only after Kafka has the events does the connector tell ASE it may discard that part of its log.

This description of the stops comes from the engineering handbook (architecture chapter) and the original project's captures; the sections that follow test each stop in the lab.

What the pipeline promises, and what it does not

The promise is at-least-once delivery: no committed change is lost, even if the connector or the network fails in the middle. The price is that after a restart some changes can arrive again. Every event carries an id, source.oqid, that lets a consumer spot the repeat. The reliability section later demonstrates this with a restart and shows the duplicates it produces. I do not claim exactly-once delivery, because that would be a different (and harder) design.

How to use this article

  • Read straight through for the full story, or jump to a section when something breaks. The section "Why is there no data?" is organised by symptom.
  • Run everything. Every command here has a script in lab/. Output blocks are real captures; the file they came from is linked under each one. Where I have not run something, I say not run.
  • Skip ahead to build once you have seen the pipeline work. The build-along starts from an empty project and reaches the same result.

Check yourself

1. Why does the connector buffer rows instead of publishing each one as it arrives?

RepAgent sends changes of transactions that are not committed yet, and some of them roll back. Publishing early would show consumers changes that never really happened. The connector publishes a transaction only after its COMMIT.

2. What does "at-least-once" mean for a consumer?

Nothing committed is lost, but after a restart the same change can be delivered again. Consumers need to tolerate repeats, for example by remembering the source.oqid of events they have processed.

2.Try it at home

Before we explain anything, let us watch a change travel from ASE to Kafka. With the container images already on my machine, the whole sequence below took 125 seconds from a clean reset to the fourth event (measured in evidence/19); expect longer on the first run, which I have not measured. Every step ends with a check: if the check does not match, stop and read "Why is there no data?" before going on.

What you need

  • Knowledge: basic SQL, a command line, and (for the build-along) the ability to read and write basic Java.
  • Software: Docker with Compose, and Node.js 18 or newer (only to rebuild this article). The build-along runs Maven inside a container, so you do not need a local Java or Maven.
  • Resources: about 15 GB of free disk and 8 GB of RAM. The ASE image alone is about 9 GB on disk. I did not measure a first-time image download on a clean machine, so I cannot give you a download time.
  • Licence: the ASE image is the Developer Edition published as datagrip/sybase. You use it under its own terms. It was last built in 2019 and runs an ASE build from 2015, so it is for learning only.

All commands are run from the repository root. The scripts used in this section (start, register-connector, changes, consume, reset) and sample-data also exist as .ps1 for Windows PowerShell; I ran them from a clean lab (evidence/22). The output below was captured with the .sh versions in Git Bash. The helper scripts used in later sections (set-tables, await-event) and everything in lab/experiments/ exist only as bash scripts, so on Windows run those in Git Bash.

Step 1. Start the lab

lab/env/start.sh

This starts four containers: ASE (cdc-lab-sybase), Kafka (cdc-lab-kafka), Kafka Connect with our connector (cdc-lab-connect) and Kafka UI (cdc-lab-kafka-ui). On first boot ASE creates the database phoenix_test and the table payment from the scripts in sybase/.

Accounts and exposure. Besides creating the database, start.sh creates two ASE logins with a random password each, kept in the git-ignored file lab/env/.lab-secrets: cdc_admin, which holds only replication_role and is used to configure and start the RepAgent, and cdc_app, which can only read and change the sample tables and is used for the scripted changes. The sa login is used only for one-time setup. Every port the lab publishes is bound to 127.0.0.1, so nothing is reachable from other machines. This is a local learning lab: TLS and SASL were not performed and nothing here claims production security. The tests behind these statements are in evidence/21-lab-security.txt (78 checks, all passed).

Check: the script ends with these lines:

ok: ASE finished first-boot init (READY)
ok: Kafka healthy
ok: Kafka Connect REST answers
ok: lab accounts cdc_admin (replication_role) and cdc_app (DML on sample tables) exist
Lab is up. Next: lab/env/register-connector.sh, then lab/env/changes.sh

Then docker ps should list four cdc-lab-* containers. You can also open Kafka UI at http://localhost:8080.

Step 2. Register the connector

lab/env/register-connector.sh

This posts connectors/sybase-cdc-phoenix.json to Kafka Connect and then starts the RepAgent inside ASE. The order matters, according to the setup script: the connector should be listening before RepAgent starts (see "Source database prerequisites").

Check: the connector and its task are RUNNING, and ASE says the RepAgent thread started. Before that you will also see ASE confirm the RepAgent retry timeout setting (10); the lab lowers it from 60 so reconnects are quick:

Replication Agent thread is started for database 'phoenix_test'.
{"name":"sybase-cdc-phoenix","connector":{"state":"RUNNING",...},"tasks":[{"id":0,"state":"RUNNING",...}],"type":"source"}

Step 3. Change some rows

lab/env/changes.sh

The script runs lab/env/changes.sql: two inserts, one update and one delete on payment.

Check: ASE prints (1 row affected) four times, then the remaining rows of the table.

Step 4. Read the events from Kafka

lab/env/consume.sh

Check: you see four events, one per change, in this order. Each line is key | value. I have shortened the source block here; the full lines are in evidence/14-lab-first-event.txt.

{"payment_id":"1"} | {"op":"c","before":null,"after":{"payment_id":"1","account_no":"ACC-1001","amount":"125.5","currency":"EUR","created_at":"2026-10-22T20:12:45.593"},"source":{...},"ts_ms":...}
{"payment_id":"2"} | {"op":"c","before":null,"after":{"payment_id":"2","account_no":"ACC-1002","amount":"80","currency":"USD",...},"source":{...},"ts_ms":...}
{"payment_id":"1"} | {"op":"u","before":{...,"amount":"125.5",...},"after":{...,"amount":"130",...},"source":{...},"ts_ms":...}
{"payment_id":"2"} | {"op":"d","before":{"payment_id":"2",...,"amount":"80",...},"after":null,"source":{...},"ts_ms":...}

Read one line carefully:

  • op is c (create, an insert), u (update) or d (delete).
  • before is the row before the change (updates and deletes). after is the row after it (inserts and updates). The one that does not apply is null.
  • source says where the change came from, including oqid, the unique, ordered id of this change. We use it later to spot duplicates.
  • The key is the table's primary key. It is quoted as a string because the column is numeric; the data types section explains why.

Starting over

To get a clean lab, run lab/env/reset.sh. It removes the four cdc-lab-* containers and their data. The next start.sh creates everything again. A faster reset that keeps the containers is not built yet.

Check yourself

1. In Step 4 the update event has both before and after. Why is that useful to a consumer?

The consumer can see exactly which column changed and what the old value was, without keeping its own copy of the row.

2. Why does Step 2 register the connector before it starts the RepAgent?

RepAgent connects to the connector as soon as it starts. The setup script (sybase/02_repagent.sql) says not to start the RepAgent until the connector listens. I did not start it too early to see what ASE does (not run); in the lab, a RepAgent whose connector was away kept retrying (see "Why is there no data?").

3.Source database prerequisites

The connector cannot read a database that has not been prepared. ASE only streams changes when four things are in place. The lab does all four for you at first boot; here is what each one does, so you can recognise the symptom when one is missing.

The four preparations

#PreparationWhere it is doneWhy it is needed
1Enable RepAgent threads: sp_configure 'enable rep agent threads', 1sybase/01_setup.sqlTurns on the RepAgent feature server-wide.
2Mark each table you want: sp_setreptable payment, truesybase/01_setup.sqlOnly marked tables have their changes sent. Unmarked tables are invisible to CDC.
3Point RepAgent at the connector: sp_config_rep_agent phoenix_test, 'enable', 'CDC_RS', 'rs_user', 'rs_password'sybase/02_repagent.sqlNames the fake Replication Server and the login it will use. This also sets the point up to which ASE keeps its log until we acknowledge.
4Add the CDC_RS entry to the ASE interfaces file: host connect, port 11752sybase/start.shRepAgent finds the connector by looking up this name.

Then one more step the first time only: start the RepAgent after the connector is listening, with sp_start_rep_agent phoenix_test. In the lab that is done by lab/env/register-connector.sh.

Why the log matters

ASE keeps log records until RepAgent says it has delivered them. If the connector is down, the log grows. The lab database enables trunc log on chkpt so ASE can still trim the log up to the point we have acknowledged; the script sybase/03_log_threshold.sql adds a threshold that raises an alert before the log fills. In a real system you must watch this: a stuck connector can eventually fill the log.

What this lab runs

The ASE image is datagrip/sybase, which reports Adaptive Server Enterprise/16.0 SP02 PL02, Developer Edition (see evidence/08-ase-facts.txt). A newer ASE (SP04 PL07 HF1 is the target of the original project) has not been run here; anything version-specific in this article is marked.

Lab-only shortcut. The lab sets net password encryption to false so the connector can check a plain login. Real systems should not do this. TLS and password encryption against the connector were not run.

Check yourself

1. You insert a row into a table and nothing shows up in Kafka. Which two preparations would you check first?

Whether the table was marked with sp_setreptable, and whether the RepAgent is running and connected (sp_help_rep_agent phoenix_test, 'process').

2. Why is the RepAgent started after the connector, not before?

RepAgent connects to the connector as soon as it starts. The setup script (sybase/02_repagent.sql) says not to start the RepAgent until the connector listens. I did not start it too early to see what ASE does (not run); in the lab, a RepAgent whose connector was away kept retrying (see "Why is there no data?").

4.Choosing what to capture

There are two filters between a table and a Kafka topic, and mixing them up is the most common reason for "I changed a row and nothing arrived".

Two filters

  1. In the database: only tables marked with sp_setreptable <table>, true send changes at all. Every table that produced events in the lab was marked this way (sybase/01_setup.sql, lab/env/sample-data.sql, lab/env/types.sql). I did not write to an unmarked table to confirm that it sends nothing (not run); this is how ASE documents the feature and how the original project's troubleshooting guide describes it.
  2. In the connector: table.include.list lists which of those tables become topics. The setting's description in SybaseCdcConfig says an empty list means every marked table and that the match ignores case; I only ran non-empty lists (not run for the empty list and for upper-case names). The next sections show what happens when a table is missing from the list.

A table must pass both. The connector config used in the lab is connectors/sybase-cdc-phoenix.json; it starts with "table.include.list": "payment".

Topic names

Each table gets its own topic named <topic.prefix>.<database>.<table>. With the lab config that is sybase.phoenix_test.payment; the topics the lab produced are listed in evidence/32. The key of each record is the table's primary key columns, for example {"payment_id":"1"} (see the first section's output, evidence/14), so all changes to one row go to the same partition in order.

One more filter: the maintenance user

The setting database.maintenance.user (default cdc_maint) names a login whose transactions RepAgent does not forward. In ordinary replication that login is the Replication Server's own writer, so its changes are not sent back in a loop. Here it is useful for the same reason: changes made by that login never appear in Kafka. I have not tested this setting in the lab (not run).

Changing the list later

You can change the list at any time with lab/env/set-tables.sh payment,customer (bash only: there is no PowerShell version, so on Windows run it in Git Bash). Two things to know, both shown in the next sections:

  • The task restarts, and RepAgent can take a while to reconnect.
  • Do not count on what happens to rows written while a table was not on the list. In my run such a row was delivered after I added the table, as a side effect of the restart; the next section explains what I know and what I did not verify.

Check yourself

1. A table is in table.include.list but was never marked with sp_setreptable. Will its changes appear?

No. The database never sends them, so there is nothing for the connector to filter.

2. What is the topic for table customer with the lab config?

sybase.phoenix_test.customer.

5.How changes are read and delivered

So far we used a connector somebody else wrote. Now we build it. The build-along has six steps, and each one ends with a check against the real ASE, so you see your own code receive real changes.

A word about "increment". In this article an increment is only one numbered step of the build. It has nothing to do with the "incremental" mode of the JDBC source connector, which polls the table with SELECT ... WHERE id > last again and again. This connector never runs a SELECT: I searched the finished source for JDBC and SQL use and found none. ASE's RepAgent reads the transaction log and pushes the changes to a listener, and building that listener is what you do here.

How each step works

  • A starter (lab/increments/NN-name/starter): the project with the code you write replaced by hinted TODOs. It compiles and every new test fails.
  • Tests that replay packets captured from a real ASE RepAgent, so what passes is what the real thing sends.
  • A live check (verify-live.sh): it stops the connector for a minute, runs your code in its place, writes a row, and passes only if the real RepAgent talked to your code correctly.
  • A reference solution (lab/solutions/NN-name) to compare with when you are stuck.

You need Docker and nothing else for the build: Maven runs in a container (lab/env/mvn.sh), so there is no local Java or Maven to install. The first build downloads the dependencies into a Docker volume; I did not test building from an empty cache without internet (not run). The scripts are bash; on Windows run them in Git Bash.

lab/increments/01-listener/verify.sh             # the unit checkpoints on your starter
lab/increments/01-listener/verify-live.sh        # your code against the real ASE (lab must be running)
lab/increments/01-listener/verify.sh solution    # the same tests on the reference solution

Each step builds on the previous solution, and the earlier tests keep running, so a later step cannot silently break an earlier one.

The pieces, and where each step fits

RepAgent --LTL--> (1) listener --> (2) parser --> (3) transaction buffer --COMMIT--> queue --> (4) mapper --> Kafka
    ^                                                                                                      |
    +----------- "get truncation" <-- (5) ack tracker <-- (6) Connect task: commitRecord() <-- Kafka ack --+

Step 1. The listener RepAgent connects to

RepAgent can only send to "a Replication Server" named in the ASE interfaces file. Your listener pretends to be one. It must answer, in order: the TDS login, connect source (two result sets), get maintenance user, get truncation, and then acknowledge each batch of LTL text with exactly one DONE. The byte-level TDS classes are given; you write the accept loop (LtlServer) and the handshake (LtlSession). Six checkpoints.

Live check, reference solution ([inc1] lines are printed by the listener):

[inc1] login user=rs_user accepted=true
[inc1] connect source MYSYBASE.phoenix_test LTL 760
[inc1] LTL 10434 bytes: distribute 1 ~*620261022 21:55:29:876,4 0x00000000000015b0...
PASS  01-listener (solution): the real RepAgent logged in, connected its source and sent LTL to your listener

ASE sent about 10 KB of LTL in one batch. It sends the changes it still holds, which can include older ones it has not yet been told it may forget.

Step 2. Reading LTL

LTL looks like text but values are length-prefixed: ~"$abc is a 3-character string, because the character after the marker is a length digit in base 64 starting at !. A tokenizer is given; you write the value decoder (LtlValues) and the grammar (LtlParser): tags, begin/commit/rollback and applied ... rs_insert|rs_update|rs_delete. An update's after image arrives with only the changed columns, so you rebuild the full row from the before image. 15 new checkpoints; 16 of 21 tests fail on the starter.

[inc2] INSERT payment before=null after={payment_id=11, account_no=LIVE011706-1, amount=1, currency=EUR, created_at=2026-10-22T22:17:18.563}
PASS  02-ltl-parser (solution): your parser decoded the row we just wrote (account_no=LIVE011706-1) from the real RepAgent's LTL

The line is Java printing a map, so strings have no quotes. The exact decimal amount is held as a string, and in Kafka it travels as a string too (see the data types section).

Step 3. Nothing is real until COMMIT

The buffer is the reason a rolled-back row never reaches Kafka. The core idea fits in a few lines:

case BEGIN  -> open.put(xid, new Open(...));
case INSERT, UPDATE, DELETE -> open.computeIfAbsent(xid, k -> new Open()).changes.add(c);
case COMMIT -> { Open o = open.remove(xid); ... return Optional.of(new CommittedTransaction(...)); }
case ROLLBACK -> open.remove(xid);

(simplified from the reference solution). The live check writes one row inside a transaction it rolls back and one in a committed transaction; your buffer must report only the second:

[inc3] COMMITTED xid=00000000000015b000804d59... rows=1 [payment:account_no=LIVE012345-1]
PASS  03-transaction-buffer (solution): the committed row (LIVE012345-1) was released at COMMIT and the rolled-back row (LIVE012345-RB) never was

Step 4. The event Kafka sees

The mapper builds the topic (<prefix>.<database>.<table>), the key (the primary key columns) and the value with op, before, after, source and ts_ms, in that order. The live check compares what your mapper builds for a real row with the shape of the real events from the first section:

[inc4] topic=sybase.phoenix_test.payment key={payment_id=19} value={op=c, before=null, after={payment_id=19, account_no=LIVE013014-1, ...}, source={server=MYSYBASE, db=phoenix_test, owner=dbo, table=payment, xid=..., user=cdc_app, seq=0, txn_rows=1}, ts_ms=...}

Step 5. Telling ASE what is safe to forget

ASE keeps its log until the connector reports a position it can free. Kafka confirms records one by one and out of order, so the reported position must never pass a transaction that is not fully confirmed. The whole rule is this loop:

private void advance() {
    while (!queue.isEmpty() && queue.peekFirst().remaining <= 0) {
        acked = queue.pollFirst().oqid;
    }
}

The live check uses two real transactions and a fake Kafka that confirms the newer one first. The watermark must wait:

[inc5] confirmed commit_oqid=…001a… watermark=null              (the newer transaction; the older is still unconfirmed)
[inc5] confirmed commit_oqid=…0017… watermark=…001a…           (the older one is confirmed: the watermark jumps to the newer)

Step 6. The connector, packaged and running

The Kafka Connect task connects the listener, parser, buffer, mapper and tracker. Only the last record of a transaction may carry the offset that says "this whole transaction is done"; if Connect crashed between two records of one transaction, the stored position must still be the one before it, so the transaction is sent again and nothing is lost. The price is a possible duplicate, as the reliability section showed. You also package everything as one JAR with the Maven shade plugin, which is the plugin Kafka Connect loads.

The live check builds your JAR, starts a separate temporary Connect worker that has only your plugin (the finished connector is stopped, not changed, and is started again afterwards), registers your connector, writes a row and waits for its event in Kafka:

ok: Connect lists your connector class (the plugin JAR is packaged correctly)
ok: your task is RUNNING
event on lab6.phoenix_test.payment: {"payment_id":"22"} | {"op":"c","before":null,"after":{"payment_id":"22","account_no":"LAB6014353-1",...
PASS  06-package-and-run (solution): your packaged connector delivered the real change (LAB6014353-1) to Kafka

Rows written during that check go to lab6.* topics, not to the sybase.* topics.

Not run

  • Running your plugin on OpenShift or IBM Event Streams, and anything with TLS or SASL.
  • Very large transactions and long outages.
  • PowerShell versions of the step scripts (they are bash only).
  • A learner actually working through the steps: the checks show the starters fail and the solutions pass, not how long a learner needs.

Check yourself

1. Step 1: why does the listener answer every batch of LTL with exactly one DONE?

RepAgent expects one answer per message. A second DONE is read later as the answer to get truncation and RepAgent aborts (see the comment in lab/solutions/01-listener/src/main/java/com/phoenix/cdc/sybase/ltl/LtlSession.java).

2. Step 2: an update arrives with only the changed columns. How do you build the after image?

Start from the before image and put the changed columns over it, keeping column order (LtlParser.command() in lab/solutions/02-ltl-parser).

3. Step 3: a transaction has no BEGIN in the batch you received. Do you drop its rows?

No. RepAgent may have restarted inside the transaction, so the buffer creates the transaction on the first row and keeps it (TransactionBuffer.accept() in lab/solutions/03-transaction-buffer).

4. Step 4: why does a delete take its key from the before image?

A delete has no after image; the deleted row's values are in before (ChangeEventMapper.key() in lab/solutions/04-connect-records).

5. Step 5: transactions A (2 records) and B (1 record) are registered; B is confirmed first. What is the watermark?

Still the old one. B is done, but A, before it, is not, and the watermark only moves past a transaction when everything before it is done (AckTracker.advance() in lab/solutions/05-acks-and-offsets).

6. Step 6: why may only the last record of a transaction carry the "done" offset?

If Connect crashed after publishing some records of a transaction, the stored position must still be the one before the transaction, so the whole transaction is sent again instead of its tail being lost (SybaseCdcSourceTask.poll() in lab/solutions/06-package-and-run).

7. Does this connector query your tables?

No. It never runs a SELECT. ASE's RepAgent reads the transaction log and sends the changes to the listener you built in step 1.

7.Resetting and restarting from a chosen point

"Start again" can mean three different things, and they behave very differently. This section separates them and then shows, with a real experiment, how to choose the point the connector restarts from. The script is lab/experiments/offsets.sh (bash only; on Windows run it in Git Bash) and its full output is evidence/37.

Three kinds of restart

What you doWhat survivesWhere it is shown
Reset the lab: lab/env/reset.sh (or reset.ps1)Nothing. Containers, the ASE database, the topics and the connector's stored position are all removed.Section "Try it at home"
Restart the connector: restart the container, or stop and resume the connectorThe stored position. The connector continues from it; a graceful restart delivered all 30 rows with no duplicates in one run, a kill right after publishing produced duplicates."Reliability experiments" (evidence 25 and 26)
Change the stored positionYou decide which position the connector reports to ASE. ASE then sends again what follows that position.This section (evidence 37)

Where the position lives

The connector's position is the commit_oqid of the last transaction Kafka has confirmed. Kafka Connect keeps it in the internal topic _connect-offsets. You can read it directly:

export MSYS_NO_PATHCONV=1    # Git Bash only
docker exec cdc-lab-kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 \
  --topic _connect-offsets --from-beginning --timeout-ms 6000 \
  --property print.key=true --property key.separator=' => '

Each record looks like this (from evidence 37):

["sybase-cdc-phoenix",{"database":"phoenix_test","server":"MYSYBASE"}] => {"commit_oqid":"00000000000015b0…0000"}

The key names the connector and the source (database and server); the value is the position. A newer record for the same key replaces the older one, so the last record is the current position. When the connector starts, its log says which position it found:

Starting Sybase CDC task for MYSYBASE.phoenix_test; last committed OQID in Kafka: 00000000000015b0…0000

The REST offsets API does not move this connector

Kafka Connect has a REST API for offsets (GET and PATCH /connectors/<name>/offsets). In the experiment, on a freshly built lab:

  • GET returned "offset": null although the topic held a position.
  • After PATCH with an older position, GET showed that older position, but when the connector was resumed it started from its own stored position, not from the one I patched.

The two disagree because the REST view and the task write the key with its fields in a different order (server, database against database, server), so they are two different keys. I confirmed the symptom; the key order is my explanation from the stored key, not something I tested further. The engineering handbook lists a related symptom (troubleshooting entry) and says it does not occur on a fresh environment; in this fresh lab it did.

Choosing the point: write the record yourself

What did work was writing the record into _connect-offsets with the exact key the task uses, while the connector is stopped:

curl -X PUT localhost:8083/connectors/sybase-cdc-phoenix/stop
printf '%s\n' '["sybase-cdc-phoenix",{"database":"phoenix_test","server":"MYSYBASE"}]|{"commit_oqid":"<older position>"}' | \
  docker exec -i cdc-lab-kafka /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server kafka:9092 \
  --topic _connect-offsets --property parse.key=true --property 'key.separator=|'
curl -X PUT localhost:8083/connectors/sybase-cdc-phoenix/resume

Result: the task log printed the position I had written, and after one new row made ASE reconnect, the three rows written earlier arrived again: the event count for the test tag went from 3 to 7 (the three rows again, plus the new row), with only 4 distinct oqid values. ASE sends again everything after the position the connector reports, as long as ASE still holds it in its log. I rewound by a few minutes; I did not test rewinding far back or beyond what ASE still holds (not run), so I cannot say what ASE does then.

Resetting to nothing

Writing a record with a null value (a tombstone) for the same key removes the position. The next start logs last committed OQID in Kafka: none (first start), and ASE again sent what it still held: the duplicated events for the test tag rose to 7 in total, from 5 distinct changes. Nothing was lost; the consumers simply see old changes again.

Before you try this anywhere that matters

  • Every rewind or reset creates duplicates for consumers. Use source.oqid to tell them apart (see "Reliability experiments").
  • Stop the connector first. I did not test writing the record while it was running (not run).
  • After each experiment the connector was RUNNING and the RepAgent was sleeping, which is its healthy idle state here. I ran this only on the local lab.
  • I did not test starting under a new connector name, which the handbook's runbook mentions as another way to reset (not run).

Check yourself

1. You rewind the stored position by a few minutes. What do consumers of the topic see?

The changes after that position arrive a second time, with the same source.oqid as before. Nothing is lost, but they are duplicates.

2. You use the REST PATCH to set the position and resume the connector. Where does it start from?

From its own stored position, not the patched one, in this lab. Write the record into _connect-offsets with the task's key instead, with the connector stopped.

3. What does "none (first start)" in the task log tell you?

That no position is stored for the connector, so it reports nothing to ASE and ASE sends again what it still holds.

8.Message keys and topic naming

Two choices shape how consumers use your events: which topic a change goes to, and which key it carries. The connector makes both choices for you, and you can see them in the output from the first section.

Topic: one per table

The topic is <topic.prefix>.<database>.<table>. With the lab config ("topic.prefix": "sybase", database phoenix_test) the topics I saw were:

sybase.phoenix_test.customer
sybase.phoenix_test.ltl_types
sybase.phoenix_test.payment

(listed with kafka-topics.sh --list in evidence/32). I did not create or configure these topics, so they have the broker defaults: the same file shows one partition and replication factor 1 for each. That is fine for a single-broker lab and is not a production setting. I did not check whether the connector or one of my own consumer scripts created each topic first, so I make no claim about automatic topic creation by the connector.

Changing topic.prefix changes the names of all topics. I did not run that change in the lab (not run); if you change it on a running pipeline, consumers must switch topics.

Key: the primary key columns

The key of each record holds the primary key columns that RepAgent flags, as JSON:

{"payment_id":"1"}  | {"op":"c", ...}
{"payment_id":"1"}  | {"op":"u", ...}
{"payment_id":"2"}  | {"op":"d", ...}

All changes to the same row carry the same key. Kafka sends records with the same key to the same partition, so a consumer sees the changes to one row in order. With only one partition, as here, that is true for the whole topic. If a table has no primary key, the connector sets no key (from ChangeEventMapper.key(); I did not test it, not run).

The key and the value are written as JSON without a schema: the connector config sets key.converter.schemas.enable and value.converter.schemas.enable to false. Consumers must know the shape of the data; the data types section lists it.

A delete is an event, not a tombstone

A delete produces a normal record with "op":"d", the old row in before, and after set to null. It does not produce a Kafka tombstone (a record with a null value). A consumer that builds a table from a topic must handle d itself.

Changing a primary key is one update event

I inserted a row with id 36544 and then ran an UPDATE that changed its id to 36545 (lab/experiments/key-change-update.sh, evidence/27). The topic received one c event for the insert and then one u event: before.id is 36544, after.id is 36545, and the message key is {"id":36545}, taken from the new row. There is no delete of the old key and no insert of the new one.

What follows for a consumer: the key changed, so the update may land in a different partition than the insert (I ran one partition, so I did not observe that). A consumer that keeps a table by key must remove before's key and add after's key when it sees u.

Check yourself

1. Two updates to the same row land in a topic with several partitions. Can a consumer see them out of order?

No. Both carry the same key, so they go to the same partition, and a partition keeps its order.

2. A consumer reads a delete event and sees after: null. Where is the data of the deleted row?

In before.

Why exact decimals are strings

Numbers in JSON are usually read as 64-bit floating point. That cannot hold every numeric(18,4) or money value exactly, and money must not drift by a fraction of a cent. The connector therefore sends exact decimal types as strings and keeps their digits as ASE stored them: smallmoney -12.34 arrives as "-12.3400", with the scale of the column. Convert them in your consumer with a decimal type, not a float.

The same applies to a numeric primary key: the key in the first section is {"payment_id":"1"}, a string, because payment_id is numeric(18,0).

Watch out for bigint. The connector writes it as a JSON number: 9223372036854775807. A JavaScript consumer reads that as a float and rounds it. A Java or Python consumer is fine. I only checked what the connector writes; I did not run a JavaScript consumer (not run).

Dates carry no time zone

Date and time values are written exactly as ASE holds them, with no zone or offset. The connector does not know the server's time zone, so a consumer must decide what zone those values mean. In the first section's output, created_at came from ASE's getdate() in the container's zone.

Types I did not test

text and image columns, unichar, unitext, very long values, and character sets other than the default (ltl.charset) were not run in this lab. The original project's notes list garbled non-ASCII text as an anticipated problem when the character set is unknown; I have not reproduced it.

Check yourself

1. A consumer reads "c_money":"99.9900" into a double and adds it to a total. What is the risk?

Floating point cannot represent all decimal amounts exactly, so totals can drift. Read it into a decimal type.

2. How would you get the bytes of c_vbin back?

Base64-decode the string: "3q2+7w==" is 0xdeadbeef.

10.Multiple tables

So far we watched one table. Real databases change several tables in one transaction, and consumers of different topics then need to know those events belong together.

Add a second table

lab/env/sample-data.sh
lab/env/set-tables.sh payment,customer

sample-data.sh (PowerShell: sample-data.ps1) creates the table customer and marks it for replication. set-tables.sh (bash only, no PowerShell version) adds it to table.include.list. The task restarts, so the next change is delayed by the RepAgent reconnect, as explained in "Why is there no data?".

Check: after you insert a customer row, a topic sybase.phoenix_test.customer has one event with "table":"customer" in its source block.

One transaction, two topics

The experiment lab/experiments/multi-table-transaction.sh (bash only; on Windows run it in Git Bash) runs this in one transaction:

begin tran
insert into customer (full_name, country) values ('TXN...', 'EG')
insert into payment (account_no, amount, currency) values ('TXN...', 42.00, 'EUR')
commit tran

Result (fields picked from the two events; full output in evidence/18-multi-table-transaction.txt):

Topicsource.xidsource.commit_oqidseqtxn_rows
sybase.phoenix_test.customer…1783002f4d59……1783…0032…02
sybase.phoenix_test.payment…1783002f4d59……1783…0032…12

Both events carry the same xid and the same commit_oqid. seq gives their order inside the transaction (0, then 1) and txn_rows says the transaction had two row changes in total. A consumer that wants the whole transaction can group events from several topics by xid. Here both tables are on the include list, so the two events match txn_rows of 2; see the caveat below before using that as a check.

What this does not give you

  • No ordering between topics. Kafka only orders records inside a partition. The two events above are in different topics, so a consumer may see the payment before the customer. Use seq if the order matters.
  • txn_rows counts every row of the transaction, not only the published ones. From ChangeEventMapper.java and SybaseCdcSourceTask.java: txn_rows is the size of the whole transaction, including rows of tables that are not on the include list, while seq numbers only the rows that were published. With an include list, a consumer may therefore see fewer events than txn_rows says. I read this in the code and did not run a test for it (not run); do not use txn_rows as a completeness check unless every table of the transaction is on the list.
  • Scale. I tested two tables and small transactions here. Large transactions are held in memory until commit; the original project saw the worker heap near 2 GB in a big test, see the handbook's test chapter (index.html).

Check yourself

1. How can a consumer tell that a payment event and a customer event came from the same transaction?

They have the same source.xid (and the same source.commit_oqid).

2. Does Kafka guarantee that the customer event is read before the payment event?

No. They are in different topics, and ordering is only kept inside a partition. Use seq.

11.Reliability experiments

The promise of this pipeline is at-least-once delivery: nothing that was committed in ASE is lost, but after a failure the same change can arrive more than once. This section checks that promise with four experiments. In each script the expected result is written in the header before the first run, and below I put what actually happened next to it. All scripts are bash (on Windows use Git Bash) and live in lab/experiments/.

1. A rolled-back transaction produces no events

rollback.sh runs two transactions: one inserts a row and rolls back, the next inserts a row and commits. ASE itself holds only the committed row. In Kafka there were 0 events for the rolled-back row and one event for the committed row. ASE does send the rolled-back row to the connector (the original project’s capture of the raw change stream, captures/ltl-types.txt, contains an insert with the text “rolled back”); the connector buffers it and, as the test shows, publishes nothing for it.

2. A transaction keeps its order

multi-row-transaction.sh runs three inserts, an update of the second row and a delete of the first row in one transaction. The events came out in that order:

"op":"c"  "MR001238-1"  "seq":0  "txn_rows":5
"op":"c"  "MR001238-2"  "seq":1  "txn_rows":5
"op":"c"  "MR001238-3"  "seq":2  "txn_rows":5
"op":"u"  "MR001238-2"  "seq":3  "txn_rows":5
"op":"d"  "MR001238-1"  "seq":4  "txn_rows":5

All five share one xid (the script printed "distinct xid values: 1"). Because they were published to one topic with one partition, Kafka kept their order. Across different topics there is no such guarantee, as the multiple-tables section explains.

3. Restarting the connector mid-stream

restart-connector.sh writes 30 rows one by one in the background and, 5 seconds in, restarts the Connect container (docker restart, a graceful stop). When the writer finished and Connect was back, I waited until all 30 rows had arrived. Result: 30 events, 30 distinct source.oqid, 0 duplicates. No row was missing, and this restart happened to produce no duplicates.

That is only one run. It does not show that restarts never duplicate; the next experiment shows they can.

4. Killing the connector right after it published

Connect saves the connector's position only every 5 seconds (offset.flush.interval.ms=5000 in connect-distributed.properties). If the process dies after rows were published but before that save, the restarted connector reports an older position to ASE and ASE sends the later rows again. crash-duplicates.sh writes 5 rows, waits 1 second, kills the container with docker kill (no graceful shutdown), starts it again, and writes a sixth row so that ASE has something to send and reconnects. Output of the first attempt:

events with tag CR004213A1: 11
distinct source.oqid: 6   (distinct rows by account_no: 6)
duplicated events:    5
oqids seen more than once:
  seen 2x  "oqid":"…008f…"
  seen 2x  "oqid":"…0092…"
  … (five in total)

All 6 rows were delivered (nothing lost) and each of the first five arrived twice with the same source.oqid. That is at-least-once delivery in action.

Timing matters. An earlier version of the experiment waited until it saw the last row in Kafka and then killed the connector, about a second later; it produced no duplicates in six events. I did not keep that output, so treat it as an observation, not evidence. The script now repeats with different delays and stops at the first duplicate; it needed one attempt.

Detecting and handling duplicates

find-duplicates.sh <topic> <tag> counts the events for a tag, counts the distinct source.oqid values and lists the ids seen more than once. In the crash run it reported 11 events and 6 distinct ids. The rule for a consumer follows from that: the id that identifies a change is source.oqid. Two events with the same oqid are the same change delivered twice; two real updates to the same row have different ones. A consumer that must not process a change twice has to remember the oqid values it has handled, or write its results idempotently (for example "set this row to these values" instead of "add 10").

I did not run a consumer that does this de-duplication, so I only show the detection (not run for a working de-duplicating consumer).

What these experiments do not show

  • Exactly-once delivery. The design does not provide it, and nothing here tests it.
  • Behaviour under heavy load, long outages or a full ASE log. The original project tested some of these; see the handbook's test chapter (index.html).
  • A crash of ASE or of Kafka. Restarting ASE in the middle of a check is planned as a separate experiment (not run).

Check yourself

1. The restart experiment delivered 30 of 30 rows with no duplicates. Does that show the pipeline never duplicates?

No. It was one graceful restart. The crash experiment, which kills the process before Connect saves its position, produced 5 duplicates. Whether duplicates appear depends on timing.

2. Two events on the payment topic have the same source.oqid. Are they two changes?

No, they are one change delivered twice. Two separate changes always have different oqid values.

3. Why did the crash script write a sixth row after restarting the connector?

ASE only notices that the connector is back when it has something to send. The extra row makes it reconnect, and the reconnect is when it sends the rows again.

4. A transaction inserts a row and then rolls back. What does the topic contain for that row?

Nothing. ASE sends the row to the connector, but the connector buffers it and publishes nothing when the rollback arrives (evidence/23: 0 events for the rolled-back row).

12.Where to go from here

You have a working pipeline and you built the connector yourself. This last section is about the distance between this local, offline learning lab and a real deployment. It does not close that distance: it tells you where it is, and it is strict about what was actually tested.

Security note: what the lab tested, and what it did not

The lab is a local, offline learning environment on one machine. Within that scope I tested, with lab/env/verify-security.sh (evidence/21):

  • every published port is bound to 127.0.0.1 and the LTL port is not published at all; a connection attempt from the machine's network address on the four published ports did not answer;
  • two ASE logins with only the permissions the lab needs (cdc_admin with replication_role only, cdc_app with data changes on the sample tables), including that each is refused the other's actions;
  • generated lab passwords stay out of git and its history;
  • scripts that take arguments reject anything outside a strict character set.

I did not test TLS or SASL anywhere: in the lab, ASE, Kafka and Kafka Connect talk in plain text on the local Docker network and on loopback. The fixed passwords in the repository (sa is the public default of the ASE image; rs_user / rs_password is the connector login) are public test values that protect nothing outside the lab. This lab is not evidence that a production deployment is secure, and nothing here claims that production security requirements were tested or met.

What changes for a real deployment (from the original project, not re-run)

  • One worker, one port. RepAgent connects to a single host and port, so the Connect cluster that runs this connector must have one replica; more replicas would send RepAgent to workers that have no listener (comment in deploy/openshift/02-kafkaconnect-eventstreams.yaml).
  • The RepAgent login travels in clear text in the setup the original project tested; the handbook rates this a high risk (security chapter).
  • Log growth. While the connector is down, ASE keeps its log. The original project reproduced the alert threshold and wrote down the emergency procedure; I did not repeat it.
  • Memory. A transaction is held in memory until its commit, so very large transactions need a larger heap.
  • Ownership. The original project's completion report (docs/COMPLETION.md) lists open questions that only the owning teams can answer, including the licensing and support position on RepAgent talking to a third-party endpoint, and who owns and supports the connector code. Its verdict for the original project is "not production-ready" (see also the handbook's readiness chapter).

Check yourself

1. A colleague says "the lab passed 78 security checks, so we can deploy it". What is wrong with that?

The checks cover a local lab: loopback-only ports, two least-privilege logins, secrets out of git, argument checks. TLS and SASL were not tested, and the fixed passwords are public test values. Nothing there says a production deployment is secure.

2. Why must the Connect cluster that runs this connector have one replica?

RepAgent connects to one host and port. Only the worker that runs the task has the listener open, so a second replica would receive RepAgent connections it cannot serve.

3. The image tag 16.0 of the ASE image looks newer than the one the lab uses. Can you switch to it?

Not on the strength of this lab. It is a different build (16 layers against 12) that was never tested here (evidence 20), so everything in this article would need to be re-run on it.
